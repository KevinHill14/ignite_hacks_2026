# Deploying to Render, step by step

Written to be followed literally. Every value you need to paste is given.

Budget about 45 minutes. Most of it is waiting for builds.

> **AFTER JUDGING: downgrade `syllabus-n8n` back to Starter.**
> It was bumped to Standard (2 GB RAM, ~$25/mo) on 2026-08-22 because n8n
> reliably OOM-crashed on Starter's 512 MB the moment it ran the real
> pipeline (PDF extraction + a live Claude call + a Calendar write need
> far more memory than sitting idle at the login screen). Starter is fine
> again once nothing needs to process a real syllabus.
> Render → syllabus-n8n → Settings → Instance Type → Starter.

---

## What you are building

Two services, from one blueprint:

| Service | Type | Reachable from |
|---|---|---|
| `syllabus-web` | Web service | The internet — this is the URL you give judges |
| `syllabus-n8n` | **Private** service | Only `syllabus-web`, over Render's internal network |

n8n holds every credential, so it deliberately has **no public URL**.

## Step 1 — Create the blueprint

1. Go to <https://dashboard.render.com>
2. **New +** (top right) → **Blueprint**
3. Connect GitHub if prompted, and authorise Render to read
   `KevinHill14/ignite_hacks_2026`
4. Pick that repo. Render finds `render.yaml` automatically.
5. Give the group a name — `ignite-hacks` is fine
6. **Apply**

Render creates both services and starts building. **It will fail or come up
half-working until you finish step 2** — that is expected, not a problem.

---

## Step 2 — Environment variables

Two services, two separate env var screens. Getting a value onto the wrong one
is the single most common way this goes wrong.

### On `syllabus-web` → Environment

`INGEST_TOKEN` is generated by Render automatically. Everything else you add
by hand:

| Key | Value |
|---|---|
| `APP_PASSWORD` | The password you give judges. **Make up a new one** — do not reuse a local test password. |
| `MAX_UPLOAD_MB` | `10` |
| `RATE_LIMIT_PER_MINUTE` | `3` |
| `RATE_LIMIT_PER_DAY` | `25` |

Then **copy the generated `INGEST_TOKEN` value** — you need it in a moment.

### On `syllabus-n8n` → Environment

`N8N_ENCRYPTION_KEY` is generated automatically. **Never change it after
credentials are saved** — doing so makes every stored credential permanently
unreadable.

Add:

| Key | Value |
|---|---|
| `EXTRACTION_MODEL` | `claude-sonnet-5` |
| `GOOGLE_CALENDAR_ID` | Your throwaway calendar ID (`…@group.calendar.google.com`) |
| `N8N_BLOCK_ENV_ACCESS_IN_NODE` | `false` |
| `WEBHOOK_URL` | Leave blank for now; step 4 fills it |

> **`N8N_BLOCK_ENV_ACCESS_IN_NODE=false` is not optional.** n8n blocks `$env`
> unless this is the literal string `false` — unset means blocked. Without it
> every calendar write fails with "access to env vars denied" and the model
> silently falls back to the wrong one. This cost us hours locally.

Save. Both services redeploy.

## Step 3 — Google OAuth redirect URI

Your existing OAuth client only trusts `localhost`. Add the deployed address.

1. <https://console.cloud.google.com/auth/clients> → click your Web client
2. Under **Authorised redirect URIs**, **keep** the localhost one and **add**:

   ```
   https://YOUR-N8N-URL/rest/oauth2-credential/callback
   ```

3. **Save**

You do not know `YOUR-N8N-URL` yet, because n8n is a private service with no
public URL. That is the chicken-and-egg in the next step.

---

## Step 4 — Connect Google (the fiddly part)

OAuth needs a browser to reach n8n, and a private service cannot be reached
from a browser. Two ways round it. **Option A is what I recommend.**

### Option A — temporarily make n8n public

1. In `render.yaml`, change `syllabus-n8n` from `type: pserv` to `type: web`
2. Commit and push. Render redeploys and gives n8n a public URL like
   `https://syllabus-n8n-xxxx.onrender.com`
3. Copy that URL. Set it as `WEBHOOK_URL` on the n8n service, **with a
   trailing slash**:
   ```
   https://syllabus-n8n-xxxx.onrender.com/
   ```
4. Add the redirect URI from step 3 in Google Cloud, using that same host
5. Open the n8n URL, create the owner account, then run the setup:
   - **Workflows → Import from File** → `n8n/syllabus-to-calendar.workflow.json`
   - Add the **Anthropic** credential (your API key)
   - Add **Header Auth**: name `X-Ingest-Token`, value = the `INGEST_TOKEN`
     you copied from the web service
   - Add **Google Calendar OAuth2** with your client ID and secret, then click
     **Connect** and sign in
   - **Activate** the workflow
6. Change `type: web` back to `type: pserv`, commit, push

Once the OAuth token is stored it keeps working, so n8n can go private again.

### Option B — migrate a local n8n

Set `N8N_ENCRYPTION_KEY` on Render to exactly the value in your local `.env`,
then export credentials locally and import them on Render. Fewer moving parts
in Google Cloud, more moving parts with files. Only worth it if Option A
fails.

---

## Step 5 — Point the web app at n8n

On `syllabus-web` → Environment, confirm:

```
N8N_WEBHOOK_URL = http://syllabus-n8n:5678/webhook/syllabus-ingest
```

That is **`http`, not `https`**, and the bare service name — it resolves only
inside Render's private network. `render.yaml` sets this already; check it
survived if you switched service types.

---

## Step 6 — Test

1. Open your `syllabus-web` URL
2. You should hit the **password page**. If you go straight to the app,
   `APP_PASSWORD` did not save.
3. Sign in, upload `syllabus_examples/CS1026-Online-Section-Winter-2026.pdf`
4. Expect ~90 seconds, then deadlines and costs, and events on your calendar

**Note the first request after idle is slow.** Render free-tier services sleep,
and n8n takes ~30 seconds to wake. Wake it with one throwaway upload before
demoing to judges.

## When it goes wrong

| Symptom | Cause |
|---|---|
| "pipeline is not listening" | Workflow not Activated, or n8n still waking |
| `401` on upload | `INGEST_TOKEN` on the web service ≠ the Header Auth value in n8n |
| "access to env vars denied" | `N8N_BLOCK_ENV_ACCESS_IN_NODE` is not the string `false` |
| Events on today's date, untitled | Old workflow version — re-import from the repo |
| `redirect_uri_mismatch` | The URI in Google Cloud is not character-for-character the callback URL |
| Calendar "value is invalid" | `GOOGLE_CALENDAR_ID` must be email-shaped. `primary` fails validation. |
| Everything 500s after a deploy | Rate-limit state resets on deploy; that is expected, not the cause. Check the logs. |
