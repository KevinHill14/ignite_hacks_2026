FIRST TIME HERE? READ docs/TEAMMATE-SETUP.md
--------------------------------------------
It assumes you have never used an API key or a .env file, and it tells you
whether you even need one. Most tasks on this list do NOT.

Short version if you are doing design, docs, mobile, or the pitch:

    git clone https://github.com/KevinHill14/ignite_hacks_2026.git
    cd ignite_hacks_2026
    npm run gen:secrets
    npm --prefix web install
    npm run web:dev

then open http://localhost:3000 and click "See a worked example". That renders
the entire product with sample data - no API key, no Google account, no cost.

If you need the live pipeline (only the extraction tasks do), Kevin will send
you the .env contents. Save that text as a file named exactly ".env" in the
repo root, then:

    npm run gen:secrets
    npm run n8n:up
    npm run n8n:setup

That last one imports the workflow, creates all credentials, and activates it.
Docker Desktop has to be running.

BUDGET: the shared Anthropic key has roughly $2.30 left. A full 5-syllabus run
costs about $0.15, so around 15 of them remain. Keep
EXTRACTION_MODEL=claude-sonnet-5, and use the worked examples for anything
that is not a genuine extraction test - they cost nothing and are instant.

THE ONE THING THAT KEEPS BITING US
-----------------------------------
Several bugs this week were the same shape: something missing or mismatched,
and code quietly substituting a plausible value instead of failing.

  - n8n blocks $env unless N8N_BLOCK_ENV_ACCESS_IN_NODE is literally "false".
    Unset means blocked. Every calendar write failed.
  - A try/catch around that silently downgraded the model to Opus. Every run
    cost 1.7x more than intended, invisibly, for hours.
  - moment.tz(undefined, tz) returns NOW rather than throwing. 18 events were
    created untitled on today's date and the pipeline reported 18/18 SUCCESS.
  - Cost dedupe compared exact strings, so "iClicker Cloud subscription" and
    "iClicker Cloud (1-term licence)" never matched and the shared item was
    billed twice. The total was wrong by $35 and nothing said so.

Each produced a confident wrong answer rather than an error. If you are adding
a fallback, ask whether a wrong-but-plausible value is worse than a crash. For
money, dates, or anything with a side effect, it is.

The same logic applies to fuzzy matching. The dedupe fix uses token-subset
comparison, which could over-match and silently DELETE real costs from the
total - a worse failure than the one it fixes. That is why check-dedupe.mjs
exists and asserts that "Studio Kit 1" and "Studio Kit 2" stay separate.

SECURITY AUDIT - 2026-08-22
---------------------------
Checked after adding the password gate. All clear:
  - No password or API key appears in ANY commit, across all history
  - .env and web/.env.local are gitignored and untracked
  - Zero NEXT_PUBLIC_ variables, so no server secret can reach the browser
    bundle. That prefix is the only thing that inlines a value client-side.
  - APP_PASSWORD never appears in client code
  - The cookie stores `expiry.HMAC(expiry, password)`. The password is the
    signing key, never the payload, and HMAC is one-way — the cookie cannot be
    reversed to recover it.
  - Cookie is HttpOnly, SameSite=Lax, Secure in production
  - Only /login and /api/login are ungated; everything else including
    /api/ingest is behind the gate
  - CSP, HSTS, nosniff, X-Frame-Options: DENY, Referrer-Policy all intact

On "should the password be encrypted": no, and it should not be. It is
configuration, not stored user data. What matters is that it never enters git,
never reaches the browser, and is never written into the cookie — all three
verified above. On Render it lives in the dashboard's env vars, which are
encrypted at rest by Render.

ROTATE BEFORE DEPLOY: the local test password is in a chat transcript. Set a
different one in Render's environment, and that is the one judges get.

[x] 8. Password-gate the web app - DONE
       Set APP_PASSWORD in .env and every page and API route requires sign-in.
       Leave it BLANK for local work and the gate is off entirely, so nobody's
       first clone hits a login wall.
       Lives in web/src/proxy.ts - NOT middleware.ts, which is deprecated in
       Next 16 and renamed. Writing middleware.ts would silently do nothing.
       Session cookie is `<expiry>.<HMAC(expiry, password)>`: the expiry is
       readable but tamper-evident, the signature cannot be replayed against a
       new expiry, and the password itself is never in the cookie. HttpOnly,
       SameSite=Lax, Secure in production. Wrong guesses cost a second each.
       Files: web/src/lib/auth.ts, web/src/proxy.ts,
              web/src/app/login/page.tsx, web/src/app/api/login/route.ts
       Verify: npm run check:auth (25 checks)
